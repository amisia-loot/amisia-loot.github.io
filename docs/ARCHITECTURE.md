# Amisia architecture

What the parts are, how data moves, and the contracts between the addon, the tools and the site.
Read this and [DECISIONS.md](DECISIONS.md) before changing anything. Change this file in the same
commit as a protocol, an export line, a saved key, a settings section or a TOC file.
`tools/tests/test_contracts.py` (run by `python3 tools/build.py check`) holds the tables marked
"(checked)" against the code, both ways.

The other documents: [DECISIONS.md](DECISIONS.md) (the user's decisions), `docs/FEATURES.md`
(every user-visible feature with version, status and the checks the user does in game; read by
`tools/features.py`) and `docs/specs` (a short spec before each larger feature, `README.md` says
when and how, `TEMPLATE.md` the headings; older drafts in `docs/superpowers`). See D-35.

Three parts:

| Part | Where | What |
|---|---|---|
| Addon | `Amisia/`, `Amisia_Raid/`, `Amisia_Gear/` | WoW Forever addon in three addons (F-202, D-130): the core `Amisia` (TOC `## Interface: 16001, 20506, 11509`; main window, settings, sync between Amisia clients, overview), the raid module `Amisia_Raid` ("Amisia: Raid", same clients; raid recording, awards, rolls, DKP/EPGP, lineup, calendar) and the gear module `Amisia_Gear` ("Amisia: Ausrüstung & Dungeons", `## Interface: 16001`, Forever only; gear/BiS/map/quests/professions/talents, collectors, all `Data/*`). On TBC Anniversary (20506) and Classic Era (11509, with SoD and Hardcore) the core and the raid module load, from their own `<folder>_TBC.toc` / `<folder>_Vanilla.toc` (the folder's TOC without the Forever parts, the gear module's without any file; written by `build.py tocs`; D-01, D-57). |
| Site | `Amisia-Website/index.html` (+ `Amisia-Website/data/*.js`) | The guild ledger on GitHub Pages; state in Supabase (`ledgers.main`). Reads the addon's export lines, writes the paste-in blocks for the addon. TBC is a read-only archive. |
| Tools | `tools/` | Python builders of `Amisia_Gear/Data/*.lua` and `Amisia-Website/data/forever.js`, the build/check/release entry point `tools/build.py`, tests in `tools/tests` and `tests/` (the addon's Lua tests). |

Folders: `Amisia/` (the core), `Amisia_Raid/` and `Amisia_Gear/` (the modules) are the addon and nothing
else (exactly what `tools/release_addon.sh` copies to the game, each with its TOC `<folder>.toc` at its
root; a file's path inside its folder is unique over the three, so "Raid/Awards.lua" names one file); `Amisia-Website/` is the site (`index.html`, its images, `data/`, the
download `Amisia.zip`, and `supabase/`, the database sources, which `.github/workflows/pages.yml`
leaves out of the deploy); `tests/` holds the addon's Lua tests and stub, `tools/` the builders and
tool tests, `docs/` the documents.

## Module map (checked)

addon folder (`tools/modules.py files` names the part). `ns` is the addon table: the core's, which the modules
share (their `Module.lua`). Every file also uses
`Locales/Locale.lua` (`ns.L`), `Core/Registry.lua`, `Core/Core.lua` and `Core/Names.lua`; the

### Load order rules

- Three addons (F-202, D-130): the core `Amisia/Amisia.toc`, the raid module `Amisia_Raid/Amisia_Raid.toc` and the
  gear module `Amisia_Gear/Amisia_Gear.toc`, both modules with `## Dependencies: Amisia`, the gear module with
  `## OptionalDeps: Amisia_Raid` (the client loads it after the raid module) and `## Interface: 16001` (Forever
  only). Each TOC lists every `.lua`/`.xml` of its folder exactly once, a path stands in one folder only, and the
  modules carry the core's `## Version` (`build.py check`: TOC against the folder, which also fails while a
  `<folder>_TBC.toc` or `<folder>_Vanilla.toc` differs from its folder's TOC without the camelot lines, the gear
  module's without any file; `build.py tocs` writes them and the modules' version).
- Every file but `Locales/Locale.lua`, `Core/LazyData.lua` (its data functions), the modules' `Module.lua` and
  the generated `Data/*` puts its body in `ns.Load(function() ... end)` right after `local ADDON, ns = ...` and
  ends with `end)`. The client loads `AmisiaDB` only after the core's files ran. `Locales/Locale.lua` (first in
  the core's TOCs) notes on the core's `ADDON_LOADED` which modules will load (installed, on for this character,
  loadable: `C_AddOns.GetAddOnInfo`/`IsAddOnLoadable`/`GetAddOnEnableState`/`IsAddOnLoadOnDemand`, the old
  globals as fallback; the gear module only on Forever) and waits for their `ADDON_LOADED`; then it reads the
  language (`ui.language`, F-199), runs the bodies, the core's, the raid module's, the gear module's, each in TOC
  order, and hands the core's event to the handlers (`ns.CoreLoaded`, which unregisters it so a second delivery
  does nothing). If something still waits at `PLAYER_LOGIN` (the client's answer was wrong), it runs them then
  and hands `PLAYER_LOGIN` on once (`ns.LoginLoaded`); a module the client loads after that runs its bodies at
  once and its `ADDON_LOADED` handlers get the core's event late (`ns.LateLoaded`). A failing body stops only
  itself (the client's error handler). `tools/tests/test_load_order.py`; D-128, D-130.
- A module's first file (`Raid/Module.lua`, `Gear/Module.lua`) runs at once: its `ns` (the client gives every
  addon its own) gets a metatable onto the core's (`_G.AmisiaCore`, `__index` and `__newindex`), so `ns.X`
  reads and writes the core's table in every file of the module; `rawget(ns, ...)` in a module sees nothing
  (use `ns.DataLoaded`). Its `ns.Load` queues the bodies as that module's part.
- A module compares the addon name of `ADDON_LOADED` with `ns.ADDON` (the core's: the handlers get the core's
  event) and that of `ADDON_ACTION_BLOCKED`/`FORBIDDEN` with `ns.OwnAddon` (the client names the addon whose code
  it refused, the core or a module); its own `ADDON` is its folder's name. Textures stay in the core's
  `Media/` (`Interface\AddOns\Amisia\Media\...`), the licences in the core's `LICENSES/`.

## Comm (addon messages)

`Core/Comm.lua`. Envelope: `<proto digit><KIND 2 letters>\t<field>\t<field>...`, at most 250 bytes,
no control characters or `|` in a field. `ns.SYNC_PROTO = 1`, `ns.SYNC_MIN_PROTO = 1`; a newer
protocol is dropped; a kind a client does not know is dropped (so new
kinds need no protocol bump). More fields than the check needs are allowed (a later client).

| Prefix | Carries | Throttle (send) |
|---|---|---|
| `Amisia` | every control kind | 10 messages burst, refill 1/s |
| `AmisiaD` | only `BL` (blob parts) | 10 messages burst, refill 1/s; leaves 260 bytes for a waiting control message |
| both | - | 1000 bytes burst, refill 500 bytes/s; queue max 200 (low priority, then data parts fall out first) |

Send queue: priority = control before data; `opts.low` entries (exchanges) go only while nothing
else waits (ttl 120 s); default ttl 60 s; `opts.key` replaces a waiting entry; `opts.when` gates it; `opts.sent` is called once it went.
Result 3/8 (throttled): back off 2^tries s, 5 tries; 11 (lockdown): hold until
`ADDON_RESTRICTION_STATE_CHANGED`; nothing is sent in the chat lockdown, in battlegrounds or arenas,
on `RAID` without a home raid, on `PARTY` without a home group (PARTY only for the routes, D-97, and the group quest state, D-110), on `WHISPER` to a name neither in the group nor in the guild (except with
`opts.anyone`: only the feedback FB and FA between a player and the author, D-61).

Receive limits per sender: 40 messages in 10 s and 20480 bytes in 60 s, else ignored for 60 s;
own echo dropped; per-kind gap below (a second message of the kind within the gap is dropped);
keyed gaps per first field (`KEYED_GAP`, 64 keys per sender). Blob parts: only on RAID or WHISPER (no
art goes to the guild; parts on GUILD are dropped unread), from a verified guild member only (an outsider's parts are dropped unread for 60 s), 3 open sets per sender, 90 open parts
and 18000 Base64 bytes per sender, a set waits 30 s for its next part (`COMM_BLOB_LOST`), a finished
set id is remembered 60 s; unpacked size max 65536 bytes; packing is the client's `C_EncodingUtil`
(CBOR, Deflate, Base64), 200 characters per part.

Chat lines of another addon (read only, never sent): `Raid/RollWatch.lua` reads the start and end
lines of a Gargul round in the raid chat and raid warnings (D-44); Amisia registers no prefix of
another addon and never answers one. The layer change (D-117) reads short layer requests ("inv layer") in the guild chat and whispers of guild members, the plain chat convention of other layer addons, never their hidden messages.

Trust words below: **member** = `ns.TrustWait(name, "member")` (in the own guild by the roster);
**officer** = officer rank (rank flag 22) in the own guild; **in group** = `ns.InMyGroup`. The
sender is always the server's sender name, never a field.

## Export format `#AMISIA 2`

Text block `#AMISIA 2 <exporter>` ... `#END`, fields split by spaces, names with `_` for the space,
free text (source name, note) always last. Rules (DECISIONS): existing lines stay byte for byte; a new
line is a new two-letter kind; the header stays `#AMISIA 2`; the site skips kinds it does not know.
Three texts use the header: the raid export (`ns.ExportText`, Core.lua), the drops text
(`ns.DropsExportText`, Drops.lua) and the wishlist text (`ns.WishExportText`, Bis.lua).
`tools/tests/test_export_format.py` reads a real export back with the site's parser.

## Settings registry

`ns.RegisterSettings{ key = "<section>", label, order, officer, expert, items = {...} }`; an item is
`{ key = "<section>.<name>", type = toggle/slider/time/choice/text/button/desc/custom, default, min, max,
step, ... }` (`forever = true` on a section or an item: shown on Forever only, D-57); a `custom` item brings `build(parent)` and `fill(frame)` (the frame sets its own height;
the loot rules' editor), it stores nothing through `ns.Set`. `ns.Get(path)` returns the stored value or the default, `ns.Set` validates and fires
`SETTING`. Every item but `custom` and `desc` carries a `tip` (its tooltip and the search read it;
`tests/test_settings_tips.lua`). `ns.SettingsSection(word)` finds the visible section a word names (key, name or
the start of the name, folded), for `/amisia einstellungen <word>` (it opens that section; another word is
searched). Each section names its tab (`group`, a key of `ns.PANEL_GROUPS`; "amisia" reads "Allgemein") and the
pages whose head button "Einstellungen" opens it (`pages`), D-49 (`tests/test_settings_pages.lua`):
`ns.SettingsGroups()` (the visible sections by tab, the tabs A to Z by their shown name), `ns.SettingsSectionsOf(page)`, `ns.SectionChanged(sec)`,
`ns.ResetSections(list)` ("Zurücksetzen" of the page, `ui.resetAll` for every section after `W.Confirm`). The
settings page (UI/Pages/Settings.lua) shows the chosen section (`ns.ShowSettingsSection(key)`, remembered in
`settings.window.section`), the sections of a page (`ns.ShowSettingsFor(page)`, with "Zurück zu <Seite>") or,
while its search box holds text, the hits of every section (`ns.ShowSettings(text)`); `ns.SettingsChosen()` tells
the main window's page list what to mark. The settings page is built from the schema. Sections (checked):

## Locales

- German is the source text and the key: `L["Vergaben"]`. German shows the key, English the entry of
  `Locales/enUS_<area>.lua` (one key in exactly one part file). The language is the player's choice
  (`ui.language`: "auto", "deDE", "enUS"; F-199), "auto" the client's (deDE German, every other English);
  it holds from the next load on (D-128). Names from the game stay in the client's language (`ns.LOCALE`). Context after `##`
  (`L["Aus##Ansage"]`). `ns.N_("...")` marks German kept as data and shown later through `L[var]`.
- Numbers and dates through `ns.Num`, `ns.FmtDay`, `ns.FmtDate`, `ns.FmtDayTime`.
- Machine formats never translate: export lines, addon messages, `AMISIA-WERTE`, talent codes, saved
  keys. Chat lines go out in the sender's language. Slash commands keep the German word plus `en =`.
- A German literal that must stay (a typed sub-word, a data key) ends its line with `-- l10n-ok`.
- `python3 tools/l10n.py check`: no German outside `L`, every key translated, none unused or twice,
  format specifiers in the same order. The game font has no `–`, `—`, `…`, arrows or bullets: use
  `·` and textures.
